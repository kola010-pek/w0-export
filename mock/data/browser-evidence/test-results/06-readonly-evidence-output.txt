--- Summary ---
Layer 1 (readonly=true only): Prevents writes via file descriptor and SQLite internal checks.
  - better-sqlite3 passes readonly option to SQLite C API (sqlite3_open_v2 with SQLITE_OPEN_READONLY).
  - SQLite rejects write operations with "attempt to write a readonly database".
  - This is documented behavior of SQLite, not just OS-level O_RDONLY.

Layer 2 (query_only=ON only): Prevents writes via SQLite engine pragma.
  - Works on a normal read-write connection.
  - Verified: writes fail with query_only=ON, succeed with query_only=OFF on same connection.
  - This proves query_only is an independent defense layer.

Layer 3 (both): Defense-in-depth. Both mechanisms active simultaneously.

Limitations (accurate description):
  - readonly:true prevents SQLite-level writes; the file is opened with SQLITE_OPEN_READONLY.
  - query_only=ON prevents SQL-level writes at the SQLite engine level.
  - Neither protects against OS-level file deletion or permission changes by other processes.
  - WAL journal mode: SQLite opens with readonly cannot create WAL files; this is a
    consequence of the readonly flag, not a separate limitation of query_only.
  - These mechanisms protect against accidental writes through the application,
    not against deliberate attacks with direct file system access.
